# Ускорение Docker-сборки C++ gateway (vcpkg)


## Короткий ответ

Да, ускорить в 2–3 раза и больше реально.
На практике самый сильный эффект даёт не смена менеджера пакетов, а правильная архитектура сборки:

1. отдельный deps-image с `vcpkg`;
2. публикация deps-image в registry;
3. обычные rebuild'ы только для кода приложения.

## Почему «так долго»

- `grpc`/`protobuf`/`drogon` — тяжёлые C++ порты, компиляция дорогая;
- `--no-cache` каждый раз убивает кэш слоёв;
- на новых машинах локально компилируется весь dependency-стек с нуля.

## Рабочая стратегия

### A. deps-image (локально)

```bash
docker compose --profile build build gateway_deps
```

### B. deps-image (общий для команды)

```bash
GATEWAY_DEPS_IMAGE=ghcr.io/<org>/richcrabs-gateway-deps:latest \
  scripts/publish-gateway-deps.sh
```

### C. daily-dev

```bash
export GATEWAY_DEPS_IMAGE=ghcr.io/<org>/richcrabs-gateway-deps:latest
scripts/dev-fast-rebuild.sh
```

## Нужно ли «скачать библиотеки в git руками»?

Обычно **нет**.

Минусы хранения бинарных библиотек в Git:
- репозиторий быстро раздувается;
- сложнее обновления и rollback;
- проблемы с платформенной совместимостью и ABI.

Гораздо лучше хранить готовые зависимости как Docker image в registry.

## Стоит ли заменить vcpkg на Conan/apt?

- **Conan 2** может дать быстрый бинарный remote cache, но миграция нетривиальна.
- **apt-only** обычно быстрее в установке, но хуже воспроизводимость и версии могут не совпадать.

Для этого проекта выгоднее оставить `vcpkg`, но убрать повторную пересборку зависимостей.

Ниже практичные варианты от самого дешёвого к более радикальному.

## 1) Оставить vcpkg, но исправить процесс (рекомендуется)

1. Не использовать `--no-cache` в обычном dev-цикле.
2. Не делать `docker compose down -v` перед каждой пересборкой.
3. Держать BuildKit включённым (`DOCKER_BUILDKIT=1`).
4. Использовать кеш компилятора (`ccache`) — уже включён в `defay1x9/Dockerfile`.
5. Триггерить полную пересборку зависимостей только при изменении `vcpkg.json`/triplet.

Ожидаемый эффект: с десятков минут до секунд/пары минут при изменениях только в `src/`.

## 2) Статическая линковка (опционально)

Плюсы:
- проще рантайм-образ (часто без `.so` рядом);
- меньше проблем с `LD_LIBRARY_PATH`.

Минусы:
- более долгая линковка;
- может увеличиться размер бинарника;
- некоторые зависимости сложнее статически собирать (в т.ч. OpenSSL/nghttp2/zlib цепочки).

Вывод: имеет смысл как runtime-стратегия, но не как главный рычаг ускорения build-цикла.

## 3) Предсобранный base-image с vcpkg-зависимостями

Подход:
- отдельный Dockerfile/target, где собираются только зависимости из `vcpkg.json`;
- пуш этого образа в registry;
- приложение строится поверх него.

Плюсы:
- на новых машинах не нужно локально компилировать весь стек зависимостей.

Минусы:
- нужен registry и дисциплина версионирования base-image.

## 4) Замена менеджера пакетов

### Conan 2

Плюсы:
- развитая бинарная модель + remote cache.

Минусы:
- миграция CMake-интеграции, рецептов и lock-файлов.

### Системные пакеты apt

Плюсы:
- быстро ставятся.

Минусы:
- старые версии, плохая воспроизводимость, разные дистрибутивы = разные ABI.

Для текущего проекта vcpkg остаётся адекватным выбором, если правильно использовать кеши.
